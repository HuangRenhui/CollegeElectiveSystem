本项目遵循 [语义化版本](https://semver.org/lang/zh-CN/) 与 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.0.0/) 规范。

## [1.4.0] - 2026-10-16

### 新增：邮件通知

补齐 1.1.0 规划中「选课成功、成绩发布的消息通知（邮件 / 站内信）」的
**邮件通道**（此前仅有站内信与微信订阅消息）。

- 新增 `MailNoticeService`、`MailProperties`、`MailConfig`，
  SMTP 参数统一收归 `elective.mail.*` 配置
- **接入点**：选课成功（`CourseSelectionServiceImpl#notifySelectionSuccess`）、
  成绩发布（`CourseGradeServiceImpl#doPushGradePublished`）
- **新增独立线程池 `mailExecutor`**，不复用 `operationLogExecutor`：
  两者可靠性要求相反——日志是审计依据「不能丢」，故队列极大且用
  `CallerRunsPolicy`；邮件是「尽力送达的提醒」，若共用线程池，
  一次 SMTP 卡顿会连带把日志写入拖住。邮件池保留默认 `AbortPolicy`，
  队列满时抛异常由调用方记录，而非让用户请求去等 SMTP
- **逐人发送，不用群发抄送**：群发会让所有收件人邮箱互相可见，属隐私泄露；
  代价是 N 次 SMTP 交互，已由异步线程池吸收
- **失败只记录不抛出**：主流程此时已提交，不应因邮件失败回滚
- **邮箱在日志中脱敏**（`zh***@stu.edu.cn`），避免邮箱泄露到日志文件
- **`ObjectProvider<JavaMailSender>` 注入**：未配置邮件时该 Bean 不存在，
  直接注入会导致启动失败
- **启动时打印就绪状态**：邮件是「配置了才生效」的能力，
  若只在发送失败时才发现未配置，排查成本很高
- 默认关闭（`elective.mail.enabled=false`）且 SMTP 参数经环境变量注入，
  未配置时静默跳过，**不影响启动与主流程**

## [1.3.2] - 2026-10-15 (3)

### 修复：微信登录接口未加入白名单

`SecurityConfig.WHITE_LIST` 缺少微信的三个接口，而它们**全部发生在
用户尚未取得系统令牌的阶段**：

| 接口 | 调用时机 | 缺失白名单的后果 |
| --- | --- | --- |
| `/wx/enabled` | 小程序登录页探测是否展示入口 | 401 → **入口永远不显示** |
| `/wx/login` | 用 `wx.login()` 的 code 换身份 | 401 → **一键登录第一步即失败** |
| `/wx/bind` | 首次绑定系统账号 | 401 → **无法完成绑定** |

接口自身逻辑完全正确，问题只在白名单，因此**编译、单元测试、静态检查
均无法发现**——只有「不携带令牌真实调用」才暴露。

修复：三者加入 `WHITE_LIST`。**不可**写成 `/wx/**`，因为
`/wx/subscribe` 系列依赖 `SecurityUtils.getUserId()`，必须保持鉴权。

## [1.3.1] - 2026-10-15 (2)

### 新增单元测试：评价汇总统计

`ReviewCalculationTests`（11 个用例），复刻
`CourseReviewMapper.xml#selectCourseReviewSummary` 的统计口径，覆盖
3 处「出错也不报错」的易错点：

1. **隐藏评价（`status = 3`）必须排除**，否则违规下架的评价仍影响均分
2. **无评价时返回 `0` 而非 `null`**（`IFNULL` 的作用），
   否则前端图表拿到 null 会渲染异常
3. **参评率分母是「已修完人数」**，不是「已选课人数」也不是「评价总数」，
   口径错了会算出超过 100% 的参评率

### 排队削峰参数说明

`queue-per-second` 默认值 50，按「目标 QPS = 峰值并发 ÷ 可接受等待时间」推算：
若某课程预计 1000 人抢选、可接受等待 20 秒，则 qps 取 50 较为合适，无需调整。

削峰与 Lua 预占的超卖防护互不干扰，分别解决
「峰值请求穿透到数据库」与「超卖」两个层次的问题。

### ⚠️ 数据库变更说明（升级已有环境时必读）

本次新增 `message_notice` 表，并**要求 `semester` 表已有
`review_start_time` / `review_end_time` 两列**。两者的生效方式**不同**：

| 变更 | 开发环境（非 prod） | 生产环境 |
| --- | --- | --- |
| 新增 `message_notice` 表 | ✅ 启动时**自动创建** | ❌ 需手工建表 |
| `semester` 新增两列 | ⚠️ **不会自动添加**，须手工 `ALTER` | ❌ 须手工 `ALTER` |

原因：`config/DatabaseInitializer` 只执行 `CREATE TABLE IF NOT EXISTS`
（且会过滤 `DROP TABLE`），**不做 `ALTER TABLE` 加列**。
「已存在的表」不会被修改，因此缺列的旧表不会被自动修复
——这正是此前 `Unknown column 'review_start_time'` 报错的根因。

补齐列（已有环境执行一次即可）：

```sql
ALTER TABLE `semester`
    ADD COLUMN `review_start_time` DATETIME NULL COMMENT '评价开放开始时间（NULL 表示不限制）'
        AFTER `select_end_time`,
    ADD COLUMN `review_end_time`   DATETIME NULL COMMENT '评价开放结束时间（NULL 表示不限制）'
        AFTER `review_start_time`;
```

### 变更

- **`SelectionSyncTask.TASK_ENABLED` 置为 `true`**：定时兜底任务默认启用，每 5 分钟执行一次
- **`syncSelectionCount` 改为三方比对**：原先只比对数据库计数，
  导致「数据库没问题、Redis 余量被写错」的场景被直接跳过，
  无法满足验收清单中「手工制造数据偏差后能校正」的要求

- **数据库侧改为一次批量查询**：用 `selectValidSelectionsByCourseIds` 一次取出
  全部课程的选课记录并按课程分组，替代逐门 `selectCount`（N 次查询 → 1 次），
  分组结果同时就是重建集合所需的成员列表
- **退课状态语义细化**：`status = 0`（已退选）按「尚未选择该课程」返回 3004；
